# Forge после рефакторинга: следующий этап

Дата: 29 сентября 2026. Проверен текущий исходный код, отчёты локальных моделей, reducer, storage, TypeScript tools и сценарии UI. Этот проход добавляет анализ и документацию; перечисленные ниже изменения runtime ещё не реализованы.

## Вывод

Следующий приоритет — надёжное выполнение небольшой TypeScript-задачи с доказуемым результатом. Для этого сначала нужны корректная синхронизация состояния, честный критерий успешности и явная полнота результатов tools. Новые страницы и дообучение пока принесут меньше пользы.

Рефакторинг улучшил разделение ответственности и убрал повторный разбор истории при стриминге. Он не устранил все гонки состояния и не доказал качество решения задач.

## 1. Приоритетные проблемы

### R01 · P1 · Устаревшая hydration восстанавливает завершённый run

**Подтверждено на reducer.** Последовательность `done → hydrate(waiting)` возвращает `busy: true` и старое подтверждение. В [run-view.ts](../src/state/run-view.ts) ветка `hydrate` не сравнивает ревизии. В [App.tsx](../src/App.tsx) запрос начального состояния и подписка на события независимы. События token/status/approval не имеют общей последовательности доставки в контракте.

Проверка воспроизводит переход состояния, но не измеряет частоту гонки в реальном IPC. Сохранённая задача от этого не запускается повторно: проблема в отображении и доступности управления.

**Предложение:** присвоить снимкам и событиям монотонную ревизию, событиям — runId/sessionId. При подключении подписаться, накопить события, применить snapshot и затем события с большей ревизией. Старые события другого run отклонять. Отдельный флаг `loading` позволит не начинать работу до начальной синхронизации.

**Критерий готовности:** перестановки snapshot/token/approval/done, повторная доставка и reload не оживляют завершённую задачу и не теряют подтверждённые сообщения. Проверить не только reducer, но и IPC-интеграцию.

### R02 · P1 · Coding evaluator не проверяет TypeScript-корректность

**Подтверждено.** [evaluate.mts](../scripts/evaluate.mts) использует `ts.transpile`, затем выполняет поведенческие assertions. Отдельной проверки типов нет. Синтетический файл с TS2322 превращается в JS, который может корректно считать сумму. Следовательно, нынешний pass не означает, что TypeScript-проект компилируется.

Дополнительно assertions склеиваются с кодом кандидата в один файл, а успех распознаётся по exit code и строке stdout. Это слабая граница доверия для более серьёзного benchmark: строка сама по себе не доказывает прохождение assertions. Проверка неизменности сигнатуры и разрешённых файлов отсутствует.

**Предложение:** считать результат по независимым критериям: разрешённые изменения, сохранение API, настоящий `tsc --noEmit`, поведенческие тесты, отсутствие регрессий. Отчёт собирает внешний evaluator. Исполнение кандидата остаётся изолированным; отдельно нужны защиты от ложного успеха и отказа тестового процесса. Для fixtures с исправлением проекта compiler approval не следует автоматически отклонять без пояснения в отчёте.

**Критерий готовности:** компилирующийся неправильный код, правильный JS с ошибкой типов, поддельный success marker и изменение сигнатуры имеют отдельные отрицательные fixtures.

### R03 · P2 · TypeScript references молча обрезаются

**Подтверждено.** [analysis-engine.ts](../electron/analysis-engine.ts) возвращает максимум 80 ссылок без `truncated/nextOffset`. На примере со 101 вхождением возвращаются 80. [language-tools.ts](../electron/language-tools.ts) дополнительно ограничивает snapshot 500 файлами/примерно 8 MB и пропускает недоступные файлы, но не передаёт эту полноту в результат worker.

Для безопасного переименования символа это существенно: агент может принять частичный список за полный. Сейчас инструмента автоматического semantic rename нет, поэтому непосредственный сценарий — неполное исследование или ручной refactoring моделью.

**Предложение:** общий envelope `{items, returned, truncated, nextOffset, indexedFiles, skippedFiles, scope}`. Разделить полноту snapshot и полноту выдачи; абсолютную полноту проекта не обещать. Не разрешать массовую semantic-операцию по частичной выборке.

**Критерий готовности:** больше 80 ссылок и больше 500 файлов дают явную ограниченность результата и доступный способ продолжить поиск.

## 2. Производительность: где нужен следующий замер

Эти пункты подтверждены чтением реализации; задержки на больших реальных проектах в этом проходе не измерялись.

| Место | Что происходит сейчас | Следующий шаг |
|---|---|---|
| [Store.save](../electron/store.ts) | Синхронная валидация и сериализация всего состояния, синхронный SQLite; предыдущий полный JSON копируется в историю | Измерить p50/p95 на растущих сессиях; затем хранить messages/changes/jobs отдельными строками и писать транзакциями только изменения |
| [state IPC](../electron/main.ts) | Возвращается всё состояние, при этом заново собирается список файлов workspace | Отдельные summary/session endpoints, пагинация истории, кэш списка файлов с явным refresh |
| [queryTypes](../electron/language-tools.ts) | На каждый запрос повторяются scan/read и создание worker/LanguageService | Worker на workspace, версии файлов и инкрементальные обновления; ограничение памяти и корректное закрытие |

| [Diff](../src/components/Diff.tsx) | Каждый смонтированный diff создаёт собственный worker | Проверить 50 одновременных changes; при проблеме — очередь и небольшой общий пул |

### Ограничение текущего UI stress test

[ui-performance.mjs](../scripts/ui-performance.mjs) посылает token events в загруженную **неактивную** сессию. Reducer получает данные, но `busy` остаётся false, а блок видимого streaming response не монтируется. Поэтому измеренные ранее 12 ms и 18.5 ms относятся к вводу/IPC/истории в этом fixture. Они не характеризуют полный активный ответ.

Кроме того, метрики печатаются без порога провала; короткий замер не проверяет накопление памяти.

**Следующий сценарий:** активный run, видимый ответ 30–60 секунд, большой финальный Markdown, открытый diff, прокрутка вверх и ввод одновременно. Несколько повторов; отчёт о p95 frame gap, long tasks, памяти и результате после done. Порог CI определить по baseline поддерживаемого runner, а не по одному замеру ноутбука.

## 3. Качество модели и harness

Сохранённые результаты `qwen2.5:1.5b` и `llama3.1:8b` дали 0/2 на двух конкретных задачах. Это не достаточная выборка для рейтинга моделей и не повод объявлять причиной исключительно размер модели.

В [повторном отчёте](./local-evaluation-v02.json) видны попытка правки до чтения, выдуманный абсолютный путь и завершение текстом после ошибки tool. [Agent.run](../electron/agent.ts) завершает цикл, когда ответ не содержит вызовов tools; отдельного условия «запрошенная правка выполнена и проверена» нет.

Предлагаемый следующий эксперимент:

1. Ввести структурированные ошибки tools: `NOT_READ`, `STALE_VERSION`, `INVALID_PATH`, `USER_DECLINED` и понятный допустимый следующий шаг.
2. Для исправимых ошибок разрешить ограниченный повтор; отказ пользователя и остановку никогда не превращать в автоматическую повторную правку.
3. Разделить статусы «ответ завершён», «правка применена», «проверка выполнена» и «задача подтверждена тестами».
4. Сравнить текущий и изменённый harness на одинаковых 10–15 fixtures. Затем расширить до React/Next и нескольких файлов.
5. Фиксировать digest модели, hash исходного кода harness, настройки и версию набора задач. Одинаковой строки версии `0.2.0` недостаточно для сравнения итераций.

## 4. Что добавить в продукт

- **Model diagnostics:** отдельно «runtime доступен», «генерация работает», «tools поддерживаются», «проверочная задача выполнена». Не выдавать один зелёный индикатор за всё сразу.
- **Context inspector:** почему выбраны эти файлы, что пропущено и когда построен snapshot. Возможность закрепить файл для задачи; измерение токенов отдельным этапом.
- **Session management:** поиск, экспорт, удаление, резервная копия, понятный объём данных. API удаления уже есть, полноценного интерфейса управления нет.
- **Training dataset review:** редактирование draft, просмотр контекста, группировка родственных задач и результаты проверки. Сначала улучшить проверку данных, потом автоматизировать обучение.
- **Accessibility:** названия icon buttons, фокус после modal/approval, клавиатурное раскрытие истории, уведомления об ошибках. Нужна ручная проверка, не только наличие aria-атрибутов.

1. R01: ревизии snapshot/events и тесты перестановки.
2. R02: критерии coding evaluator; R03: полнота tools.
3. Короткий измеримый эксперимент по восстановлению после tool errors.
4. Реалистичный длительный UI benchmark и профилирование storage.
5. Пользовательский tutorial на задаче, которую агент действительно выполняет.
