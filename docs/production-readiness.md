# Forge: аудит готовности к продакшену

> Исторический аудит v0.1. Статус исправлений v0.2 и оставшиеся ограничения: [production-progress.md](./production-progress.md). Номера строк ниже относятся к прежней версии. `scripts/audit-repros.mts` теперь запускает регрессионные проверки исправлений.

Дата: 29 сентября 2026. Объект: текущий исходный код Forge 0.1.0.

## Вывод

Текущая версия подходит для личного использования как ранняя alpha на доверенных проектах. Для публичной beta сначала нужны сохранность файлов и истории, восстановление выполняющихся задач и проверяемые границы доступа. Затем — инструменты, которые действительно используют структуру TypeScript-проекта, и измерение качества решения задач.

Electron и React можно оставить. Основная работа — усилить существующий harness и вынести его состояние из интерфейса. Дообучение стоит развивать после появления воспроизводимой оценки базовой модели.

Это инженерный аудит кода и несколько локальных воспроизведений, не полный security pentest и не сертификация приватности.

### Что проверено сейчас

- `npm test`: 13/13 тестов проходят.
- `npm run typecheck`: проходит.
- `npm audit`: известных уязвимостей в установленном дереве не найдено на момент проверки. Это не проверка безопасности собственного кода.
- Шесть дополнительных сценариев воспроизведены на временных файлах и тестовом HTTP-сервере. Чужие проекты и пользовательские данные не использовались.
- Прочитаны код Electron, provider, agent, storage, training, UI, сборка и существующие тесты.
- Нативный smoke-тест и реальный ответ Ollama были проверены при создании v0.1; в рамках этого аудита повторно не запускались. Реальное обучение весов не проверялось.

Результаты: [production-audit-results.json](./production-audit-results.json).
Повтор: `npx tsx scripts/audit-repros.mts`. Скрипт специально подтверждает существующие недостатки; после исправлений соответствующие assertions надо заменить регрессионными тестами.

## 1. Что уже стоит сохранить

- Sandbox renderer, context isolation и отключённая Node integration.
- Узкий preload bridge, проверка отправителя IPC, Zod-проверки входящих аргументов.
- Loopback-only provider, запрет редиректов и фильтрация cloud-моделей.
- Подтверждение записи и запуска компилятора, проверка устаревшего содержимого файла.
- Ограничение шагов, отмена, раздельные provider и harness.
- Обучение только по явно сохранённым примерам, локальные артефакты и offline-параметры MLX.

Эти меры полезны, но renderer sandbox не ограничивает файловый доступ и сеть дочерних процессов.

## 2. Приоритет P1: до публичной beta

### F01. Модель видит обрезанный файл, но может заменить его целиком

**Подтверждено воспроизведением.** `electron/agent.ts:143` сохраняет полный прочитанный текст в `readFiles`, затем `:215` обрезает результат до 24 000 символов. `write_file` принимает полную замену файла. Модель не получает ни признака обрезки, ни инструмента чтения диапазона.

В тестовом файле было 30 043 символа; модель получила 24 000 без завершающего экспортируемого символа. Harness допустил предложение полной замены без этого хвоста. Правка была отклонена тестом, исходный файл сохранён. Это не обход подтверждения: риск возникает, если пользователь одобрит внешне правдоподобную неполную замену.

**Изменение:** чтение диапазонов строк с `truncated`, общим количеством строк и hash версии; точечный `replace_text`/patch с проверкой ожидаемого фрагмента; запрет полной перезаписи файла после неполного чтения. Показать удаления и итоговую область изменения до подтверждения.

**Критерий:** тесты на длинные и Unicode-файлы, неполное чтение и изменение файла редактором во время review; хвост файла никогда не исчезает из-за неявной обрезки.

### F02. Два экземпляра приложения могут потерять историю и датасет

**Подтверждено на двух экземплярах Store.** `electron/store.ts:31` сериализует записи только внутри одного объекта. Каждый writer сохраняет целиком свой snapshot и использует общий `state.tmp`. В `electron/main.ts` нет single-instance lock.

В воспроизведении первый writer сохранил пример, второй со старым snapshot изменил модель и сохранился: пример исчез. Одновременные записи также могут конфликтовать на временном файле; этот отдельный вариант не воспроизводился.

**Изменение:** сразу добавить блокировку второго экземпляра; затем транзакционное хранилище, предпочтительно SQLite, с отдельными таблицами sessions/messages/runs/changes/examples/jobs и миграциями. Один процесс владеет записью. Настройки могут остаться отдельным небольшим JSON.

**Критерий:** второй запуск активирует существующее окно; конкурентные операции не теряют записи; тесты прерывания процесса и восстановления.

### F03. Одобренные правки и активные задачи не имеют надёжного журнала

**Вывод из кода.** `electron/workspace.ts:84` напрямую перезаписывает файл через `writeFile`. История сохраняется перед запуском и в `finally` (`electron/agent.ts:92`, `:236`). Изменения, pending approvals и активные jobs не входят в `AppState`. Состояние review хранится в React (`src/App.tsx:150`).

При аварии после записи файла, но до финального сохранения, файл может быть изменён без сохранённой истории этой операции. После перезагрузки renderer он не может запросить текущий approval; backend может продолжать ждать решения. При завершении приложения нет ожидания финального flush (`electron/main.ts:181`). Проверка stale content полезна, но не является атомарным compare-and-swap; конкурентное изменение между проверкой и записью остаётся возможным.

**Изменение:** сохранять run ID, события и снимок состояния до/после каждого побочного эффекта; запись через временный файл в той же директории и rename с сохранением нужных атрибутов; backups/checkpoints; обнаружение конфликтов. Восстановление approval после reload. Завершённые действия при восстановлении повторно не выполнять.

**Критерий:** аварийное завершение до записи, после записи и перед фиксацией результата даёт определённый восстанавливаемый статус. Undo восстанавливает нужную версию, сохраняя последующие пользовательские изменения либо показывая конфликт.

### F04. «100% private» пока шире технических гарантий

**Вывод из кода.** `electron/agent.ts:248` и `electron/training.ts:86` запускают процессы с правами пользователя и наследуют весь `process.env`. Ограничения сети renderer на них не распространяются. Подтверждение пользователем есть — это не скрытый запуск — но оно не изолирует недоверенный компилятор или выбранный executable.

Loopback проверяет адрес сервера, а не внутреннее поведение отдельного runtime. Cloud-функции Ollama можно отключить настройкой или `OLLAMA_NO_CLOUD=1`, с перезапуском runtime; см. [официальный FAQ Ollama](https://docs.ollama.com/faq#how-do-i-disable-ollama-cloud-features).

**Изменение:** документировать модель угроз; разделить режим чтения и выполнение доверенного проекта; whitelist переменных окружения; отдельный executor с ограничениями файлов, сети и ресурсов на уровне ОС/контейнера для заявленного поддерживаемого режима. Для внешнего runtime показывать, что Forge проверяет, а что остаётся ответственностью пользователя. Проверять egress всего набора процессов в release-тестах.

Изоляция зависит от ОС. Нельзя выдавать Node worker, директорию `cwd` или offline-переменные за OS sandbox. И нельзя обещать защиту от скомпрометированной ОС или произвольного пользовательского runtime.

**Критерий:** в поддерживаемом изолированном режиме тестовый executor не читает файл вне разрешённых путей и не устанавливает внешнее соединение; env содержит только разрешённые значения. Offline-сценарий работает после предварительной установки зависимостей и весов.

### F05. Политика исключения файлов неполная

**Подтверждено.** `electron/workspace.ts:3` использует фиксированный список имён. `.gitignore` не учитывается. Тестовый `private/customer.txt`, исключённый через `.gitignore`, появился в списке и был доступен через `read_file`.

Это не доказывает отправку данных наружу: модель локальная. Проблема в неожиданном включении файлов в контекст и последующем сохранении tool output в истории. `.gitignore` сам по себе не является политикой безопасности.

**Изменение:** единая политика list/read/search/write; `.gitignore` для обычного обхода, отдельный `.forgeignore` для запрета доступа, настраиваемые denied paths, видимый пользователю список разрешённых областей. Проверять ограничения и при прямом запросе пути. Secret scanning — дополнительная защита, а не обещание обнаружить любой секрет.

**Критерий:** исключения нельзя обойти прямым `read_file` или `write_file`; одинаковое поведение поиска и чтения; тесты вложенных правил и платформенных путей.

### F06. Повреждённое состояние не валидируется и не восстанавливается

**Подтверждено частично.** `electron/store.ts:22` делает `JSON.parse` и spread без схемы. Файл `{"sessions":null}` принят без ошибки загрузки. Далее код ожидает массив и вызывает `.find`/`.filter`. Синтаксически сломанный JSON останавливает запуск целиком (`store.ts:25`).

**Изменение:** версия схемы, валидация после чтения, миграции, последняя исправная копия, экран восстановления с сохранением повреждённого оригинала. Ошибка записи должна откатывать изменение в памяти либо явно отмечать несохранённое состояние.

**Критерий:** предыдущая версия данных мигрирует; неверное поле и оборванный JSON не лишают пользователя доступа ко всему приложению; есть экспорт и восстановление.

## 3. Приоритет P2: качество и устойчивость агента

### F07. Лимиты provider и последовательность tool calls нужно исправить

**Подтверждено двумя воспроизведениями.**

- `electron/provider.ts:103` накапливает tool calls, но лимит `:116` считает только content/thinking/неразобранный buffer. Поток из 11 NDJSON-фрагментов с аргументами на 1 100 000 символов прошёл заявленный лимит 1 000 000. Ограничения Zod на этапе выполнения не ограничивают накопление ответа provider.
- `electron/agent.ts:134` выполняет только первые 8 вызовов, сохраняя в истории исходный ответ целиком. В следующем запросе тест увидел 9 заявленных вызовов и только 8 результатов. Реакция конкретной модели на такую историю может различаться.

**Изменение:** проверять структуру каждого stream chunk; учитывать общее число байтов, число вызовов и размер аргументов до накопления; возвращать результат или явную ошибку каждому вызову. Типизированные ошибки, retry только для безопасных сетевых этапов, без повторения записи файла.

### F08. Контекст и поиск не масштабируются на настоящий проект

**Из кода.** Контекст жёстко равен 16 384 (`agent.ts:119`), сохраняются последние 20 нетехнических сообщений без tool results (`:105`). Во время одного запуска история растёт без бюджета токенов. Поиск последовательно перечитывает максимум 1 600 файлов; ограничения глубины/числа файлов применяются молча. Ответ «No matches» не сообщает о неполном поиске. Крупный репозиторий может оказаться представлен случайным алфавитным подмножеством.

**Изменение:** явные `complete/truncated`, постраничный поиск, отмена обхода; быстрый локальный индекс символов и зависимостей; контекст по релевантным файлам; бюджет входных и выходных токенов с резервом для ответа. Сохранять структурированную историю tools и решений, сжимать её с возможностью повторно получить исходные данные. Подбирать размер контекста под модель и память.

**Критерий:** при превышении лимита пользователь и модель видят неполноту; измерены время поиска и UI latency на фиксированном большом fixture; длинная сессия не теряет исходную задачу без явного сообщения.

### F09. Сейчас специализация TypeScript преимущественно находится в prompt

`shared/types.ts:110` содержит полезные инструкции, но инструментов поиска definitions/references, типов символов, diagnostics или безопасного rename пока нет. Единственная проверка — `node_modules/typescript/bin/tsc --noEmit` из корня.

**Изменение:** добавить TypeScript Language Service в отдельном worker: project discovery, symbol search, definitions/references, diagnostics, rename preview. Его API рассчитан на выборочные запросы и отдельные синтаксические/семантические диагностики; см. [TypeScript Language Service](https://github.com/microsoft/TypeScript/wiki/Using-the-Language-Service-API).

Далее — выбор нужного package/tsconfig в monorepo; pnpm/workspaces; React hook/accessibility checks; Next router/version/server-client boundaries; запуск целевых тестов и сборки через контролируемый executor. Исходная проверка проекта до изменений позволит различать старые и новые ошибки.

`--noEmit` не стоит считать запретом любых дисковых изменений: incremental compilation сохраняет `.tsbuildinfo`; см. [TypeScript incremental](https://www.typescriptlang.org/tsconfig/incremental.html). Нужна отдельная политика для артефактов проверки.

**Критерий:** агент находит и переименовывает символ по ссылкам, объясняет diagnostics с путями и позициями, проверяет затронутый пакет и показывает реальный результат тестов.

### F10. Нет оценки способности решать coding tasks

`scripts/smoke.mjs:59` просит модель вернуть фиксированную строку **без tools**. Это проверяет интеграцию, но не решение задач. Тесты agent loop используют запрограммированные ответы HTTP fixture. Отсутствие ошибок в них не означает, что модель корректно чинит React/Next-проект.

**Изменение:** начать с 30–50 версионированных задач как проектного ориентира: баги типов, refactoring, hooks, маршруты, несколько файлов, незнакомые API, prompt injection в комментариях, отказ от правки, ошибки runtime. Каждая задача — исходный snapshot, критерии, поведенческие тесты и ограничения разрешённых изменений.

Измерять pass rate, регрессии, лишние изменения, неверные вызовы tools, latency до первого токена и до решения, peak memory, число пользовательских вмешательств. Зафиксировать model digest, параметры, версию harness и окружение. Число 30–50 — предложенный стартовый объём, не статистически достаточная универсальная норма. Релизный порог определить после baseline.

## 4. Training Lab: от запуска процесса к улучшению модели

### F11. Сохраняемые примеры часто лишены контекста

`src/App.tsx:277` сохраняет только ближайший user prompt и выбранный assistant message. Файлы, tool calls, проверки, исходная задача из предыдущих ходов и версия модели не сохраняются в примере. Ответ «исправил компонент» сам по себе почти бесполезен как обучающий образец.

`electron/training.ts:6` удаляет дубликаты только по точному prompt; конфликтующие ответы заменяются последним. Первые 20% примеров становятся validation. Родственные задачи и варианты одного фрагмента кода могут попасть в разные части. Отдельного test set нет. Метка Reviewed в UI не подкреплена отдельным статусом проверки.

**Изменение:** schema примера с происхождением, snapshot контекста, model/skill/harness version, проверками, лицензией/правами на данные, статусом draft/reviewed/rejected. Отдельно хранить полноценные tool trajectories. Разделять по проекту/семейству задачи; фиксировать seed и manifest; держать test set вне training/validation.

### F12. Training job не управляется как долгоживущая задача

`electron/training.ts:41` посылает только SIGTERM; нет эскалации, контроля дерева процессов и таймаутов. Состояние jobs не восстанавливается из `AppState`. Логи на диске не имеют ротации. Agent inference и MLX training могут одновременно претендовать на память. Конфигурация формы теряется при размонтировании страницы.

**Изменение:** durable job records, preflight Python/MLX/model/память/диск, блокировка или очередь ресурсоёмких jobs, ограничение логов, корректный stop/kill, checkpoint/resume, запись версий зависимостей и hash датасета/модели. Успех должен означать проверенный набор артефактов; exit 0 недостаточно для вывода об улучшении качества.

MLX предоставляет отдельные команды обучения, оценки, генерации и fusion; это разные этапы, а поддержка экспорта зависит от архитектуры. См. [MLX LoRA guide](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md).

**Рекомендуемая последовательность:** curated dataset → короткий LoRA run → baseline vs adapter на held-out tasks → ручное принятие кандидата → поддерживаемый export/import → повторная оценка после конвертации → быстрый rollback на исходную модель.

До готовности этой цепочки оставить Training Lab явно экспериментальным. Не делать автоматическое обучение на всех чатах и автоматическое продвижение последнего checkpoint.

## 5. Интерфейс, архитектура и выпуск

### UI и состояние

`src/App.tsx` — 1 664 строки, весь интерфейс обновляется через верхнеуровневое состояние. Каждый фрагмент текста обновляет stream, перерисовывает Markdown и вызывает smooth scroll (`:186`). На длинных ответах возможны лишняя работа и неудобный скролл; реальные задержки ещё не измерялись. `diffLines` выполняется синхронно в renderer.

Разделить страницы и hooks; ввести reducer/store по run ID; буферизовать отображение токенов; прокручивать только если пользователь находится внизу; виртуализировать историю и длинные diff. Ошибки должны оставаться в истории run, а не исчезать через 6,5 секунды. Нужны Error Boundary, восстановление задачи, undo, поиск/экспорт/удаление сессий, управление хранением данных, сохранение черновиков, русский интерфейс и accessibility-проверка.

### Разделение процессов

Сохранить Electron main как небольшой слой жизненного цикла, политики и IPC. Вынести orchestration/provider в отдельный процесс; indexer/TypeScript service — в отдельный worker; выполнение проекта — в executor с явно заданной изоляцией. Training controller управляет Python-процессом и durable jobs. Один storage owner ведёт журнал и данные. Отдельный worker повышает устойчивость, но сам по себе не создаёт security boundary.

### Выпуск

`package.json:54` сейчас собирает только directory target. Нет CI, миграционных release-тестов, схемы обновлений и настроенного процесса подписи/notarization. Рекомендуемый первый поддерживаемый target — macOS Apple Silicon, на котором уже проверялся MVP. Windows/Linux добавлять с отдельной матрицей тестов и исполнителя.

Для macOS нужны воспроизводимый pipeline, подписанные/notarized артефакты, проверка чистой установки/обновления/удаления и сохранности данных. См. [Electron Code Signing](https://www.electronjs.org/docs/latest/tutorial/code-signing). Обновления и диагностический экспорт сделать явными действиями пользователя, чтобы сохранить offline-first поведение.

Пересмотреть `file://`, перейти на ограниченный app protocol и настроить Electron fuses после выбора executor. **Не отключать RunAsNode вслепую:** текущий `typecheck` зависит от `ELECTRON_RUN_AS_NODE`. Рекомендации и семантика: [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security), [Electron Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses).

Для open source добавить CONTRIBUTING, SECURITY с каналом приватного сообщения об уязвимости, поддерживаемые версии runtime, model-license policy, dependency/SBOM проверку и changelog. MIT приложения не меняет лицензии сторонних весов и датасетов.

## 6. Порядок реализации

| Этап | Основная работа | Условие завершения |
|---|---|---|
| A. Сохранность и управление задачами | F01–F03, F06: range reads, patch, checkpoints, single instance, transactional store, run journal | Crash/reload/конкурентное редактирование не приводят к тихой потере данных; pending review восстанавливается |
| B. Приватная beta | F04–F05, F07: политика файлов и исполнения, provider limits, непротиворечивые tools | Негативные тесты доступа/сети и malformed streams проходят; обещания продукта соответствуют проверяемым границам |
| C. TypeScript specialist | F08–F10: контекст, Language Service, monorepo, tests, baseline evaluation | Есть измеренное качество на реальных задачах и отчёт о регрессиях при смене модели/harness |
| D. Production release | Packaging/signing, CI, upgrade/recovery, UX на длинных сессиях, локальная диагностика | Чистая установка и обновление проверены на поддерживаемой ОС; можно восстановить данные и собрать очищенный отчёт о сбое |
| E. Проверяемое дообучение | F11–F12: происхождение данных, jobs, evaluation, адаптеры | Дообученная модель проходит отдельный test set и может быть заменена исходной без потери рабочего окружения |

Базовую оценку из этапа C стоит начать уже на A, чтобы видеть влияние каждого изменения harness. Дальнейшее развитие Training Lab не должно блокировать выпуск надёжного локального агента.

## Первое практическое изменение

Начать с F01: заменить неявную обрезку структурированным чтением диапазонов и добавить точечные правки с checkpoint. Это напрямую защищает код пользователя и одновременно повышает эффективность небольшой локальной модели, которой не придётся заново генерировать весь файл.
