# Карта проекта: что дать локальной модели перед началом работы

Когда пользователь открывает TypeScript-проект, агенту сначала нужно понять, где искать код. Отправлять всё содержимое репозитория в каждый запрос неудобно: вместе с полезными файлами в контекст попадёт много материала, который не относится к задаче.

В Forge для этого появилась карта проекта. Она служит оглавлением: показывает пути, символы и номера строк, импорты и выбранные зависимости. Исходный код агент читает отдельными инструментами перед правкой.

## Как Forge строит карту

Анализ запускается при открытии проекта и обновляется перед каждой задачей. Сначала применяется файловая политика: исключённые пути, `.gitignore`, `.forgeignore` и ограничения чтения. Затем для подходящих файлов собираются метаданные.

Для TypeScript и JavaScript используется AST — синтаксическое дерево исходного текста. Из него извлекаются имена объявлений и импорты. Из `package.json` берутся версии нескольких значимых зависимостей, включая TypeScript, React и Next.js. Эти данные помогают ориентироваться в проекте, но не заменяют семантический анализ типов.

Разобранные записи кэшируются локально и повторно используются, если hash содержимого файла не изменился. Это экономит повторный разбор AST. Текущая реализация всё ещё перечитывает файлы для проверки hash: кэш не означает полного отсутствия файлового ввода-вывода.

## Что попадает в запрос

В запрос передаётся ограниченная выборка карты. Записи ранжируются по совпадениям слов задачи с путями и символами; некоторые конфигурационные файлы и точки входа получают дополнительный приоритет. Это простая эвристика, а не семантический поиск и не полноценный граф зависимостей.

Если карта не вместилась, Forge удаляет целые записи, сохраняя корректность формата. Заголовок сообщает, сколько записей показано. Отсутствие файла в этой выборке не означает, что его нет в проекте: остаются инструменты поиска и чтения.

Есть и ограничения самого индексирования. Поэтому важно различать «показали часть существующей карты» и «не смогли полностью проиндексировать проект». Для больших monorepo эти состояния особенно существенны.

## Почему формат выбирает модель

В Settings доступны compact text, JSON и Markdown. В режиме Auto Forge спрашивает локальную модель, какой из этих форматов ей удобнее, и кэширует ответ для endpoint и имени модели. Пользователь может выбрать формат вручную.

Это удобная настройка представления. Но самооценка модели не доказывает, что выбранный формат использует меньше токенов или повышает точность. Текущая оценка размера приблизительна и основана на длине текста, а не на точном tokenizer выбранной модели.

Кроме того, кэш предпочтения пока привязан к имени модели. Если заменить веса под тем же именем, старое предпочтение останется. В следующей версии стоит учитывать digest модели и версию схемы карты.

## Как проверить, полезна ли карта

Нужен эксперимент с одинаковой моделью, одинаковыми задачами и фиксированными настройками. Сравнить можно четыре варианта: без карты, compact, JSON и Markdown.

Для каждого варианта полезно измерять:

- долю решённых задач;
- количество обращений к чтению и поиску;
- число неверно выбранных файлов;
- фактический размер входного контекста, если runtime сообщает его;
- время до применённой и проверенной правки.

Уменьшение контекста само по себе ещё не успех. Если после сокращения модель теряет важный файл и чаще ошибается, выигрыш по размеру не оправдывает потерю качества. Такой сравнительный эксперимент в Forge пока не выполнен.

## Что карта не меняет

Карта не даёт модели право редактировать файл без чтения и проверки версии. Имена файлов, символов и комментарии остаются данными проекта, а не инструкциями с повышенными полномочиями.

Карта хранится в локальном SQLite и не записывается в репозиторий. Она содержит метаданные кода, поэтому относится к тем же пользовательским данным, что история и checkpoints. Отдельно установленный runtime Ollama остаётся самостоятельной частью системы, которую пользователь настраивает для локальной работы.
