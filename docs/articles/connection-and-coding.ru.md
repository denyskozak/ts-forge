# Модель отвечает. Почему агент всё ещё не исправляет код?

В Forge есть кнопка Test connection. Она полезна: помогает проверить адрес Ollama, найти установленную модель и получить от неё настоящий ответ. Но зелёный результат этой проверки ещё не означает, что агент способен исправить ошибку в проекте.

Эта разница обнаружилась в наших собственных проверках. Локальная модель отвечала на короткий запрос, а две небольшие coding-задачи закончились без применённых исправлений. Сохранённые отчёты позволяют увидеть, где именно прервалась работа.

## У подключения и задачи разные критерии

Проверка подключения отвечает на несколько узких вопросов: доступен ли runtime, есть ли выбранная модель, сообщает ли она поддержку tools и может ли сгенерировать текст. Без выбранной модели кнопка выполняет только discovery.

Для исправления кода нужны дополнительные действия. Агент должен найти файл, прочитать нужную версию, правильно вызвать инструмент редактирования, получить разрешение, сохранить правку и проверить результат. Ошибка на любом из этих шагов оставляет задачу нерешённой, даже если сама модель продолжает отвечать.

В сохранённом запуске `qwen2.5:1.5b` модель попыталась заменить фрагмент до чтения файла. Harness отклонил операцию. Затем модель объяснила ошибку текстом и попросила пользователя прочитать файл, хотя инструмент чтения был доступен ей самой. В другом случае она передала выдуманный абсолютный путь.

Это наблюдения о конкретной модели, настройках и версии harness. Две задачи не дают основания для общего вывода обо всех локальных моделях. Они дают конкретные сценарии, которые стоит исправлять и повторять.

## Что должен делать harness

Harness — код, который управляет циклом модели, инструментами, разрешениями и состоянием задачи. Он проверяет действия модели независимо от её объяснений. В Forge, например, нельзя полностью заменить существующий файл после неполного чтения, а точечная правка проверяется относительно прочитанной версии.

Следующий полезный шаг — помочь модели восстановиться после понятной ошибки инструмента. Вместо одного произвольного текста можно возвращать код `NOT_READ` и следующий допустимый шаг: прочитать указанный относительный путь. Количество повторов нужно ограничивать. Отказ пользователя должен завершать предложенное действие, а не запускать попытки обойти отказ.

Это предложение для следующей версии. Сейчас цикл Forge может завершиться обычным текстовым ответом после ошибки tool.

## Как измерять настоящий результат

Для задачи «исправь функцию» недостаточно ответа «готово». Нужны проверяемые условия:

- изменены только разрешённые файлы;
- сохранена требуемая сигнатура;
- TypeScript проверяется без ошибок;
- поведенческие тесты проходят;
- соседние сценарии не сломаны.

Наш начальный evaluator уже выполняет поведенческие assertions в ограниченном процессе. Но текущий аудит выявил пробел: перед выполнением он транспилирует TypeScript без отдельного typecheck. Поэтому даже будущий зелёный результат этого evaluator потребует осторожной интерпретации до исправления проверки.

Полезный отчёт должен показывать не только pass/fail, но и место остановки: ошибка пути, неверный вызов tool, отсутствие правки, ошибка типов или неправильное поведение. Тогда можно различать проблему модели, интерфейса инструмента и самого теста.

## Что это значит для пользователя Forge

Используйте Test connection для настройки локального runtime. После этого проверяйте агента на небольшой задаче с понятным исходом. Просматривайте diff и результат проверки, а не только итоговое сообщение модели. Если проверка не выполнялась, это должно быть видно отдельно.

Дообучение стоит оценивать тем же способом: на зафиксированных задачах и по фактическому результату. Иначе красивый ответ после обучения легко принять за улучшение coding-навыков, которого тесты ещё не подтвердили.
